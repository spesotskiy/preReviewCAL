# Задание на доработку PreReviewCAL (по результатам прогона на старой базе)

Финальная спецификация доработок с учётом согласованных правил. Задачи сгруппированы по темам и привязаны к кодам правил (`CAL001`–`CAL035`) и файлам проекта.

---

## 1. Критические ошибки (компиляция и семантика)

### 1.1. Склейка токенов при удалении скобок (`CAL021`)
- **Файл:** `internal/rules/parens_rules.go` (`fixRedundantParensInBody`)
- **Проблема:** `IF NOT(_SalesHeaderExt.GET(...)) THEN` после удаления `(` превращается в `IF NOT_SalesHeaderExt.GET(...) THEN`.
- **Решение:** при удалении `(` или `)` проверять соседние символы слева и справа. Если удаление приведёт к склейке двух идентификаторов/ключевых слов/чисел (например, `NOT(` -> `NOT `, `)THEN` -> ` THEN`), заменять удаляемую скобку на пробел `" "` вместо пустой строки `""`.

### 1.2. Защита методов и свойств `DotNet` / `Automation` / `OCX` (`CAL033`, `CAL020`)
- **Файлы:** `internal/rules/format_rules.go` (`applyKeywordCasing`), `internal/rules/parens_rules.go` (`fixCallParensInBody`)
- **Проблема:** `_ServerDocumentFile.Delete(_ServerDocumentFileName)` превращается в `.DELETE(...)` (не компилируется, т.к. методы `.NET` регистрозависимы). Также `CAL020` может ошибочно добавить `()` к `.NET`-свойствам (например, `.Count`).
- **Решение:** передавать область видимости переменных в `applyKeywordCasing`; для получателей с типом `DotNet`, `Automation`, `OCX` запрещать изменение регистра членов после `.` (`CAL033`) и автодобавление `()` (`CAL020`).

### 1.3. Строгий анализ схемы таблиц для `WITH ... DO` и обязательный `--symbols-dir` (`CAL005`)
- **Файлы:** `internal/rules/with_rule.go`, `internal/cal/builtins.go`, `internal/objectfile/symbols_dir.go`, `internal/cli/cli.go`, `internal/config/config.go`
- **Проблема:** без схемы таблицы `CAL005` эвристически префиксирует неизвестные идентификаторы и портит системные enum (`ACTION::LookupOK` -> `_SQLQuery.ACTION::LookupOK`). Кроме того, `WorkspaceIndex` не индексирует процедуры таблиц/объектов (`SetUseADO`, `AddLine0`).
- **Решение:**
  1. Сделать флаг `--symbols-dir` **строго обязательным** в CLI при включённом `CAL005` (завершать запуск с понятной ошибкой, если флаг не передан).
  2. Добавить все системные enum-типы NAV 2017 (`ACTION`, `DATATYPE`, `EXECUTIONMODE`, `REPORTFORMAT`, `SECURITYFILTER`, `TEXTENCODING`, `TRANSACTIONTYPE`, `CLIENTTYPE`, `OBJECTTYPE`, `TESTPERMISSIONS` и др.) в `GlobalBuiltins` и не префиксировать их перед `::`.
  3. Расширить `WorkspaceIndex` / `TableSchema`: индексировать не только поля таблиц (`FIELDS`), но и публичные процедуры таблиц и объектов.
  4. Отключить слепую эвристику в `CAL005`: если схема целевой таблицы/объекта не найдена в `--symbols-dir`, не выполнять подстановку для данного `WITH`-блока и выдавать `warning`.

### 1.4. События NAV 2017 (`[Integration]`, `[Business]`, `[EventSubscriber]`) (`CAL003`, `CAL011`)
- **Файлы:** `internal/rules/vars_rules.go` (`runUnusedParamRule`), `internal/rules/naming_rules.go` (`runSuffixRules`)
- **Проблема:** проверялись только AL-атрибуты `IntegrationEvent` / `BusinessEvent`, а NAV 2017 использует `[Integration]` / `[Integration(...)]` и `[Business]` / `[Business(...)]`.
- **Решение:**
  1. Распознавать издателей событий по атрибутам `Integration`, `Business`, `IntegrationEvent`, `BusinessEvent` (без учёта регистра).
  2. Полностью исключить издателей событий (`[Integration]`, `[Business]`) из `CAL003` (`unused-param`) и `CAL011` (`param-suffix`).
  3. Для `[EventSubscriber]`: в `CAL003` сохранять предупреждение (`warning`), если параметр не используется в теле подписчика (без автоудаления), а в `CAL011` — текущее предупреждение без автоправки.

### 1.5. Конфликт имени переменной с системной функцией (`Time` vs `TIME`) (`CAL010`, `CAL011`, `CAL033`)
- **Файлы:** `internal/rules/naming_rules.go`, `internal/rules/format_rules.go` (`applyKeywordCasing`)
- **Проблема:** в `GetValueAsTime(...) Time : Time;` присваивание `Time := DT2TIME(Value);` превращалось в `TIME := DT2TIME(Value);`.
- **Решение:**
  1. В `CAL033` проверять область видимости и левую часть `:=` — никогда не переводить в UPPERCASE объявленные переменные, параметры и `Return Value`.
  2. Если имя локальной переменной, `Return Value`, параметра или глобальной переменной совпадает с системной функцией (`GlobalBuiltins`), переименовывать её с добавлением суффикса **только при таком конфликте**:
     - локальная переменная / `Return Value` -> `+ L` (например, `Time` -> `TimeL`);
     - параметр -> `+ P`;
     - глобальная переменная -> `+ G` (например, `Time` -> `TimeG`).
  3. Всегда выдавать пользователю `warning` о таком переименовании (учитывая проверку лимита 30 символов и коллизий имён; для обычных `Return Value` и глобальных переменных без конфликта суффиксы не добавляются).

## 2. Ошибки отступов и позиционирования блоков (`CAL030`)

### 2.1. Ошибочные сдвиги блоков в diff/anchored-режиме и после вложенных `IF`/`ELSE`
- **Файл:** `internal/rules/format_rules.go` (`applyAnchoredIndentation`, `applyIndentation`)
- **Проблема:**
  1. `pendingOldSingleStmtIndents` не сбрасывался на строках `... THEN BEGIN`, из-за чего внешний `ELSE` протекал внутрь вложенных `BEGIN ... END` и сдвигал изменённый блок влево (кейс `// LCG PSY NAV-46641 23.11.2026 <<`).
  2. После цепочки вложенных `IF ... THEN ... ERROR(...);` следующий блок получал лишний сдвиг вправо (кейс `// LCG PSY NAV-46638 27.10.2026 <<`).
- **Решение:**
  - Переписать трекинг контекста в `applyAnchoredIndentation` на полноценный стек блоков (`BEGIN`/`END`, `CASE`/`END`, `REPEAT`/`UNTIL`, многострочные условия, однострочные открыватели), чтобы `... THEN BEGIN` корректно открывал блок и не оставлял «висящих» внешних `ELSE`/`THEN`.
  - Покрыть оба реальных фрагмента регрессионными тестами.

### 2.2. Неверный сдвиг веток внутри `CASE`
- **Файл:** `internal/rules/format_rules.go` (`applyIndentation`, `applyAnchoredIndentation`)
- **Проблема:** ветка `400:` после `200: BEGIN ... END;` получала лишний сдвиг `+2`.
- **Решение:** гарантировать возврат стека на уровень меток (`CASE + 2`) сразу после закрытия ветки (`END;` или одиночного оператора `;`).

### 2.3. Выравнивание парных маркеров кода (`<<` / `>>`)
- **Файл:** `internal/rules/format_rules.go` (`applyIndentation`)
- **Проблема:** закрывающий маркер `// LCG NEO STR29268 23.05.2022 >>` после `IF NOT LineSkipL THEN` сдвигался на `+2` относительно открывающего `// LCG NEO STR29268 23.05.2022 <<`.
- **Решение:** отслеживать стек открытых маркеров `<<` и выравнивать соответствующий закрывающий маркер `>>` строго по отступу открывающего `<<`.

## 3. Форматирование управляющих конструкций (`CAL030`, `CAL031`)

### 3.1. Обновлённые правила `IF / THEN / ELSE` (обновляет `CAL031` и тесты `c50030`)
- **Файлы:** `internal/rules/format_rules.go`, `README.md`, `testdata/cases/cal030_034_formatting/`
- **Требования:**
  1. **Однострочный `IF`:** `THEN` остаётся в строке с `IF`; тело без `BEGIN` переносится на следующую строку со сдвигом `+2`; `ELSE` выравнивается под `IF`, его тело — на следующей строке `+2`:
     ```cal
     IF Condition THEN
       Do()
     ELSE
       DoElse();
     ```
     (Исключения, остающиеся в строке с `THEN`/`ELSE`: `THEN BEGIN`, `ELSE BEGIN` и хвостовой комментарий `// ...`.)
  2. **Многострочный `IF` (и `WHILE`):**
     - Продолжения условия выравниваются под первым выражением условия (`IF ` -> `+3`, `WHILE ` -> `+6`).
     - `THEN` выносится на отдельную строку ровно под `IF`.
     - **`THEN BEGIN` всегда в одной строке** (заменяет старое поведение `CAL031` с переносом `BEGIN` на отдельную строку):
     ```cal
     IF Condition1 AND
        Condition2
     THEN BEGIN
       DoSomething();
     END;
     ```
     Аналогично без `BEGIN`:
     ```cal
     IF (Cust."Overprice Customer Group" = '') AND
        (Cust."Customer Type" = Cust."Customer Type"::Customer)
     THEN
       ERROR(...);
     ```
     И аналогично для многострочного `WHILE ... DO BEGIN` (`DO` / `DO BEGIN` на отдельной строке под `WHILE`).
  3. **`ELSE IF` и `END ELSE IF`:** `IF` переносится на новую строку со сдвигом `+2` под `ELSE` (или под `END` в связке `END ELSE`):
     ```cal
     IF Condition THEN BEGIN
     END ELSE
       IF Condition2 THEN
         DoSomething();
     ```

### 3.2. Форматирование `CASE ... OF`
- **Файл:** `internal/rules/format_rules.go`
- **Требования:**
  1. `ELSE` в `CASE` сдвигается на `+2` от `CASE` (на одном уровне с метками веток).
  2. Однострочное тело ветки (`200: EXIT(TRUE);`) переносится на следующую строку со сдвигом `+2` под меткой.
  3. `BEGIN` в ветке `CASE` и в ветке `ELSE` всегда переносится на новую строку со сдвигом `+2` под меткой/`ELSE`, тело ещё `+2`, `END;` выравнивается под `BEGIN`:
     ```cal
     CASE X OF
       Condition1:
         BEGIN
           DoOne();
         END;
       200:
         EXIT(TRUE); // LCG PSY NAV-46640 20.10.2026
       ELSE
         BEGIN
           Processed := FALSE;
         END;
     END;
     ```

### 3.3. Форматирование `REPEAT ... UNTIL`
- **Файл:** `internal/rules/format_rules.go`
- **Требование:** `REPEAT` всегда на новой строке со сдвигом `+2` (например, после `IF SalesLineL.FINDSET() THEN`), `UNTIL` выравнивается ровно под `REPEAT`:
  ```cal
  IF SalesLineL.FINDSET() THEN
    REPEAT
      ...
    UNTIL SalesLineL.NEXT() = 0;
  ```

### 3.4. Разделение нескольких команд в одной строке
- **Файл:** `internal/rules/format_rules.go`
- **Требование:** если в одной строке записано несколько операторов через `;` (например, `_SalesLine.MODIFY(FALSE); CheckSignCorrDocRules`), переносить каждый последующий оператор на новую строку с тем же отступом (не затрагивая `;` внутри строк, комментариев и скобок).

## 4. Лимит длины строки (132 символа) и многострочные выражения

### 4.1. Ограничение длины строки — 132 символа
- **Файлы:** `internal/config/config.go`, `internal/rules/format_rules.go`
- **Требование:**
  - Параметр конфига `maxLineLength` (по умолчанию `132`).
  - Выполнять перенос строк длиннее `maxLineLength`, в том числе строк, ставших длиннее после разворачивания `WITH` (`CAL005`).
  - Если строка превышает 132 символа и не может быть безопасно разбита (например, длинный строковый литерал `'...'` или длинный комментарий), не ломать её и выдавать `warning`.

### 4.2. Многострочные вызовы функций (в т.ч. `ERROR`)
- **Требование:**
  - При переносе длинного вызова строка оканчивается на `(`, аргументы переносятся на следующие строки со сдвигом `+2` и разбиваются с соблюдением лимита 132 символа:
    ```cal
    CreateMockWebSetupJsonViaSOAP(
      GTDApiMgt.GetGTDSelectionAPI(), GetWebServiceName(), SOAPUrl, 'Selection');

    Assert.AreEqual(
      FORMAT(SalesHeader."Document Date", 0, '<Year4>-<Month,2>-<Day,2>'),
      HeaderDict.GetValueAsText('Posting Date'), 'Posting Date');
    ```
  - В `applyIndentation` сохранять сдвиг `+2` для строк продолжения внутри незакрытых `(...)`.

### 4.3. Многострочные присваивания (`:=`)
- **Требование:** строки продолжения многострочного присваивания сдвигаются на `+2` относительно строки с `:=`:
  ```cal
  EnableGTDReselection :=
    (Rec.Функциональность = Rec.Функциональность::МежОфис) OR
    (Rec."Document SubType" = Rec."Document SubType"::External);
  ```

### 4.4. Многострочный / длинный оператор `IN [...]`
- **Требование:**
  - Если строка с `IN [...]` укладывается в 132 символа и уже однострочная — остаётся в одну строку:
    ```cal
    IF Value IN [Value1, Value2, Value3] THEN
    ```
  - Если строка длиннее 132 символов или уже многострочная — разбивать по элементам (запятая в конце строки, без leading comma):
    ```cal
    IF Value IN
      [Value1,
       Value2,
       Value3]
    THEN
    ```
    (`[` сдвигается на `+2` от `IF`, последующие элементы выравниваются под первым элементом на `+3` от `IF`, закрывающая `]` в конце последнего элемента, `THEN` на отдельной строке под `IF`.)

## 6. Очистка мёртвого кода, пустых конструкций и комментариев

### 6.1. Очистка пустых веток и пустого `CASE`
- **Файл:** `internal/rules/format_rules.go` (или отдельный проход очистки до форматирования)
- **Требования:**
  1. Удалять пустую секцию `ELSE;` внутри `CASE`.
  2. Удалять ветку `CASE` с пустым телом (`"Order Status"::New: ;`), **если в `CASE` нет секции `ELSE`**.
  3. Если в `CASE ... END;` не осталось исполняемого кода — удалять конструкцию `CASE` целиком (при вызове функции в выражении `CASE Fn() OF` — не удалять молча, выдавать `warning` о возможных побочных эффектах).

### 6.2. Удаление пустых триггеров (Table, XMLport и др.)
- **Файлы:** `internal/rules/vars_rules.go`, `internal/objectfile/parser.go`
- **Требование:**
  - Если триггер (в `FIELDS` таблицы, `PROPERTIES` таблицы/XMLport/страницы/отчёта, `ELEMENTS` XMLport) не содержит исполняемого кода и комментариев (изначально или после удаления неиспользуемых переменных `CAL001`, например `OnValidate=BEGIN END;`, `OnPostXMLport=BEGIN END;`) — удалять свойство триггера целиком (`OnValidate=...;`, `OnPostXMLport=...;`).
  - **Исключения:** не удалять `OnLookup` (в NAV пустой триггер `OnLookup` меняет поведение UI, отображая кнопку `...`) и `OnRun` в Codeunit.

### 6.3. Комментарии `{...}`, `//` и маркеры кода (новое настраиваемое правило, например `CAL035` / `commented-code`)
- **Файлы:** `internal/config/config.go`, новый файл `internal/rules/comments_rules.go`, `internal/rules/format_rules.go`
- **Параметры в `.prereviewcal.json`:**
  - `codeMarkerPattern` — regex маркера кода. Значение по умолчанию:
    `^\s*//\s*LCG\s+[A-Za-z]{2,4}\s+(?:[A-Za-z]+-?\d+)\s+\d{2}\.\d{2}\.\d{4}(?:\s*(?:<<|>>).*)?$`
    *(покрывает `// LCG PSY NAV-46638 27.10.2026 <<`, `// LCG LEB STR26165 02.02.2022 >>`, `// LCG IR STR14758 20.08.2020 <<`, `// LCG AL STR119 17.09.2008` и т.п.)*
  - `commentedCodePattern` — regex для распознавания закомментированного C/AL-кода в `//`-строках (настраивается под реальную базу; по умолчанию матчит строки с `:=`, `;` в конце, ключевыми словами `IF`/`THEN`/`ELSE`/`BEGIN`/`END`/`CASE`/`REPEAT`/`UNTIL`/`FOR`/`WHILE`/`WITH`/`EXIT`, вызовами процедур/методов).
  - `keepCommentPrefix` — префикс «нужного» поясняющего комментария (по умолчанию `-`, т.е. `// - ...` / `//- ...`).
- **Поведение:**
  1. **Блочные комментарии `{...}`:**
     - Никогда не пытаться анализировать и не менять отступы/содержимое внутри `{...}`.
     - Inline-комментарии `{...}` (на одной строке с валидным кодом, например `FALSE {OzonOnly}`, `ERROR( {'...'} ...)`) оставлять как есть, ничего не двигая внутри.
     - Отдельные (не-inline) блочные комментарии `{...}` (однострочные на отдельной строке и многострочные) — удалять, если правило включено; если выключено — сохранять их исходные позиции без сдвигов.
  2. **Строчные комментарии `//`:**
     - Если строка совпадает с `codeMarkerPattern` — **оставить** (считается маркером кода).
     - Если после `//` (и пробелов) строка начинается с `keepCommentPrefix` (`// - ...`) — **всегда оставить** (явно защищённый поясняющий комментарий).
     - Если строка совпадает с `commentedCodePattern` — **удалить**.
     - Обычные поясняющие комментарии, не совпавшие с `commentedCodePattern`, — **оставить**.
  3. **Пустые маркеры кода:**
     - Если после удаления закомментированного/пустого кода между парными маркерами (`<<` и соответствующий `>>`) не осталось исполняемого кода (и защищённых комментариев) — удалить оба маркера.

### 6.4. Замена строковых литералов на глобальные `TextConst` (новое правило `CAL006` / `hardcoded-textconst`)
- **Файлы:** `internal/config/config.go`, `internal/rules/textconst_rule.go`, `internal/rules/engine.go`
- **Порядок выполнения:** после `CAL004` (`local-textconst`), чтобы новые константы не конфликтовали по имени и `@ID` с перенесёнными локальными `TextConst`, и до форматирования/переноса по 132 символам (`CAL030`–`CAL034`).
- **Параметры в `.prereviewcal.json`:**
  - `languages`: список языковых кодов (по умолчанию `["ENU", "RUS"]` — записывается `ENU=<val>;RUS=<val>` с одним значением).
  - `excludeFunctions` / `excludePatterns`: настраиваемые исключения для технических вызовов/строк (например, SQL-запросы `EXEC`/`SELECT`, ключи JSON/словарей и т.п.).
- **Требования:**
  1. Искать строковые литералы **во всех выражениях** кода и заменять их на глобальные текстовые константы с возрастающим номером `<N>` (пропуская занятые имена в глобальном `VAR`).
  2. **Суффикс по контексту функции:**
     - внутри `ERROR(...)`, `FIELDERROR(...)` -> `TextConst<N>Err`;
     - внутри `CONFIRM(...)` -> `TextConst<N>Qst`;
     - внутри `MESSAGE(...)`, `STRSUBSTNO(...)`, `STRMENU(...)`, `DIALOG.*` и остальных выражений -> `TextConst<N>Msg`.
  3. **Пример замены:**
     - `STRSUBSTNO('Документ номер %1', DocNo)` -> `STRSUBSTNO(TextConst1Msg, DocNo)` + в глобальный `VAR`:
       `TextConst1Msg@<NextID> : TextConst 'ENU=Документ номер %1;RUS=Документ номер %1';`
  4. **Исключения (не заменять):**
     - Литералы **без пробелов** (одиночные слова, коды, ключи, фильтры: `''`, `'OPEN'`, `'Selection'`, `'<>0'`, `'NAV-46640'`, `'GTD_REVERT'`).
     - Коды из заглавных букв/цифр/пробелов/знаков без строчных букв (например, `EXIT('SOME CODE 5')`).
     - Технические шаблоны без слов (только плейсхолдеры/знаки пунктуации, например `STRSUBSTNO('%1 %2', ...)` или `'%1 %2 - %3, %4, %5'`).
     - Технические контексты: `SETFILTER`, `SETRANGE`, 3-й аргумент `FORMAT`, `CALCDATE`, `DELCHR`, `CONVERTSTR`, `STRPOS`, `CASE`-метки, сравнения `=`/`<>`/`IN`, а также строки, попадающие под `excludeFunctions` / `excludePatterns`.
  5. **Дедупликация:** при повторном появлении идентичного строкового литерала с тем же суффиксом в одном объекте переиспользовать уже существующую глобальную `TextConst`.
  6. **Экранирование NAV `TextConst`:** корректно экранировать значения со спецсимволами (`;`, `=`, `,`, `"`, ведущие/хвостовые пробелы) по формату C/SIDE.
